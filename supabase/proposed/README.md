# 보안 강화 SQL (제안 · 서버 미적용)
**Supabase에는 아직 적용하지 않았습니다.** 로컬 PGlite로 기존 `supabase/*.sql` 전체 체인 위에서 실행·검증했습니다(`tests/code-hardening.test.cjs`).

## 정책
- 학생은 **반·번호 + 6자리 코드**로 접속합니다(현 1·2학년이 함께 있는 신청은 현재 학년도 고릅니다). 서버는 반·번호로 학생을 먼저 찾고 그 학생의 코드 해시와 비교합니다. 없는 반·번호와 틀린 코드는 똑같이 "반·번호 또는 코드가 맞지 않습니다."라고 답합니다.
- **첫 접속 때 받은 코드를 새 6자리로 바꿔야** 하고(처음 코드는 이후 무효), 잊으면 교사가 학생별로 재발급합니다. 다른 학생과 코드가 겹쳐도 됩니다(반·번호로 구분).
- **학생 단위 잠금**(`course_code_locks`, 학생 id 기준)
  - 연속 실패 5회 → 그 학생만 10분 잠금(시간이 지나면 자동 해제).
  - 누적 실패 10회(= 10분 잠금 두 번) 뒤 또 실패 → **교사가 풀 때까지** 잠금. 학생 한 명에게 시도할 수 있는 코드는 최대 약 10개(백만 개 중).
  - 성공하면 연속 실패 수만 0으로. 누적 실패 수·잠금 횟수는 교사 해제나 코드 재발급 때 초기화됩니다(중간에 본인이 성공해도 누적 상한은 그대로).
  - 잠긴 동안에는 올바른 코드도 받지 않습니다. 첫 접속 코드 변경에서 현재 코드를 틀려도 실패로 셉니다.
  - **접속지(IP)·이벤트 전체 제한은 없습니다**(학교 공용 IP에서 몇 명의 오타로 학교 전체가 잠기던 문제 제거). 없는 반·번호의 실패는 잠글 학생이 없어 기록하지 않습니다.
- 교사 화면(웹 수강신청 → 신청 카드): **학생 접속 잠금 · 코드 재발급** 버튼 → 실패 기록이 있는 학생별 상태(잠김·약 N분 남음 / 잠김·교사 해제 필요 / 실패 n회)와 학생별 **잠금 해제**, 학생별 코드 재발급(잠금도 함께 해제). **학생 잠금 전체 해제**는 그 신청의 모든 학생 잠금·실패 기록을 지웁니다.
- 코드는 학생 id + 서버 후추로 해시(`code_hmac`)합니다. 같은 코드라도 학생마다 해시가 다릅니다. 교사 로그인 도메인 제한은 하지 않습니다.
- 코드만 받던 기존 입구(`get_scoped_course_application(p_event, p_code)`)는 내부 토큰·구형 32자리 코드만 받고 6자리 코드는 거절합니다(반·번호 없이 대입하는 길 차단). 기존 함수 체인이 이 이름을 내부에서 부르므로 이름은 유지합니다.

새 RPC: 학생용 `get_course_login_form`, `get_student_course_application`, `save_student_course_application`, `change_course_code`(반·번호를 받도록 인자 변경) / 교사용 `get_course_code_locks`, `unlock_course_student`, `unlock_course_event`(의미 변경: 학생 잠금 전체 해제), `reissue_course_code`.

## 적용 순서 (Supabase 대시보드 → SQL Editor, 한 파일씩 전체 붙여넣고 Run)
1. 기존 `supabase/upgrade-*.sql` 이 모두 적용된 상태여야 합니다(마지막 `upgrade-reselection.sql`).
2. **신청을 받고 있지 않은 시간**에 `01-code-hardening.sql` 실행 — 기존 학생 6자리 코드를 학생별 소금 해시로 변환합니다(백만 개 표 사용, 수 초). 이후 기존 코드로 처음 접속하는 학생은 새 코드를 정하게 됩니다.
3. **바로 이어서 앱(`supabase-client.js`, `index.html`, `styles.css`)을 배포**합니다. 새 앱은 새 RPC를 부르므로 SQL보다 먼저 배포하면 학생 접속 화면에 "신청 서버 설정이 필요합니다"가 뜨고, 예전 앱은 SQL 적용 뒤 "반·번호와 개인 코드를 함께 입력해야 합니다. 새로고침…" 안내를 받습니다(둘 다 안전하게 실패).
4. `02-next-round-student-id.sql` — 다음 차수 생성 시 학번이 이어지게 합니다(`upgrade-stable-student-ids.sql` 필요).
5. `03-retention-purge.sql` — (선택) 학년도 종료 +180일 뒤 자동 삭제. `pg_cron` 예약은 주석 안내.

## 되돌리기
- 01: `01-rollback.sql` 실행 + 이전 앱으로 되돌린 뒤 각 신청에서 **"전체 학생 코드 재발급"** 을 눌러 새 코드를 나눠 주세요(원본 코드는 저장하지 않아 복원 불가). 컬럼(`code_hmac` 등)은 남겨도 무해합니다.
- 02: 파일 안의 `old_text`/`new_text` 를 서로 바꿔 다시 실행.
- 03: `drop trigger course_events_purge_after on public.course_events; drop function public.purge_expired_course_events(); alter table public.course_events drop column purge_after;` 와 `cron.unschedule`.

## 잠금 방식 비교
| | 접속지(IP) 기준(이전 초안) | 학생 기준(현재) |
|---|---|---|
| 무엇을 세나 | 접속지별 10분 5회 + 신청 전체 10분 100회 | 학생별 연속 5회 / 누적 10회 |
| 학교 공용 IP | 학생 5명 오타로 학교 전체 10분 잠김 | 오타 낸 학생만 잠김 |
| 대입 상한 | 접속지를 바꾸면 계속 시도, 신청 전체로는 10분 100회 | 학생당 약 10회 후 교사 해제 필요 |
| 학생 입력 | 코드만 | 반·번호(+학년) + 코드 |
| 장난(일부러 잠그기) | 한 명이 전체를 잠글 수 있음 | 반·번호를 아는 사람이 **특정 학생**을 잠글 수 있음 |
| 해제 | 시간 경과 / 교사 전체 해제 | 10분 자동(1·2번째) → 교사 학생별 해제, 전체 해제, 재발급 |

## 알아둘 한계 (결정 필요)
- **남을 일부러 잠그기**: 반·번호는 쉽게 알 수 있어, 장난으로 다른 학생을 잠글 수 있습니다(최대 2번은 10분 뒤 자동 해제, 그다음은 교사 해제). 교사 화면 안내문에 "본인 확인 후 해제"를 적어 두었습니다. 잦다면 연속 기준을 늘리거나(`course_authenticate_student`의 `5`, `10`) 재발급으로 대응하세요.
- **학생 존재 여부**: 문구는 같지만, 잠금 안내는 실제 학생에게만 나오므로 같은 반·번호로 5번 틀려 보면 그 반·번호가 있는지는 알 수 있습니다(이름·코드는 드러나지 않음).
- 반·번호는 명렬의 값과 그대로 비교합니다(앞의 0은 무시). 명렬의 반이 "1" 이 아닌 다른 표기면 학생이 찾지 못합니다.
- 구형 32자리 긴 코드는 반·번호 없이 계속 쓸 수 있습니다(128비트라 대입 불가).

## 위계(선이수) 점검 (서버 변경 없음 · 경고만)
- **서버 SQL을 적용할 것이 없습니다.** 위계는 모든 과목에서 학생 화면 경고만 하고, 서버는 위계를 검사하거나 저장을 막지 않습니다(사용자 결정).
- 앱(`course-checks.js`)이 수강신청을 만들 때 학생 화면 경고에 필요한 정보를 기존 jsonb에 싣습니다.
  - `course_events.subjects[학년][i].requires`: 그 과목의 선이수 조건 `[{ name, designatedSemester?, options: [이 신청의 과목명], prior?: "elective" }]`(편제표 이전 학년 지정 과목으로 이미 충족되는 조건은 싣지 않음)
  - `course_events.selection_groups[i].checks`: 학기별 지정·기준 학점, 교과(군) 필수 학점 기준, 3년 누계
  - `create_course_event`는 과목의 `subject`·`credit`·`semester`, 그룹의 `id`·`grade`·`name`·`count`·`courses`·`semester`만 검사하므로 다른 키는 그대로 저장되고, 학생 조회(`courses`·`groups`)와 다음 차수 생성(`create_next_course_event`, 과목·그룹 객체를 복사)에서도 유지됩니다. 규칙이 없는 예전 신청은 그대로 동작합니다(학생 화면에 점검표가 나오지 않음).
- 예전에 만든 신청의 `checks.blockPrerequisites` 값은 앱이 무시합니다(경고만).
- 검증: `tests/course-checks-sql.test.cjs`(PGlite, 기존 체인 + 01 위에서 점검 정보 보존·다음 차수 복사, 위계 위반 선택도 저장됨, 테스트봇 위반 시도 저장).
