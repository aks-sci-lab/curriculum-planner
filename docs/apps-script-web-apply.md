# 웹 수강신청 — 교사 본인 구글 계정에 저장하는 방식(Apps Script) 시제품

- 상태: **시제품**. 앱(index.html·supabase-client.js)에는 연결하지 않았습니다. 파일은 `apps-script/` 폴더와 `tests/apps-script.test.cjs`뿐입니다.
- 목적: 신청 자료(학생 성명·학년·반·번호·선택)를 공용 서버가 아니라 **신청을 만든 교사의 구글 스프레드시트**에만 두기. 개인 Gmail 계정 전제(학교·교육청 구글 계정은 쓰지 않음).
- 이 문서에서 **'확인 못 함'** 이라고 적은 것은 이 작업 환경에서 실제 구글에 요청할 수 없어 확인하지 못한 것입니다. 사용자가 자기 계정에 배포해 `apps-script/load-test.html`로 확인해야 합니다.

## 1. 구조

```
학생 브라우저 ──(우리 홈페이지의 학생 화면)──┐
                                             ├─ fetch POST(text/plain, JSON) ─→ 교사의 Apps Script 웹 앱(doPost)
교사 PC의 앱 ──(관리 열쇠)──────────────────┘                                   │
                                                                                ├─ Script Properties: 관리 열쇠, 코드 해시용 소금, 신청 설정
                                                                                ├─ 시트 '명렬_<id>': 학생 한 줄(코드는 해시만)
                                                                                └─ 시트 '기록_<id>': 제출 1건 = 한 줄(학생별 마지막 줄이 유효)
```

- 스크립트는 얇게: 저장과 규칙 검사만 합니다. 학생 화면·교사 화면·엑셀은 지금처럼 앱이 만듭니다. 화면을 고쳐도 교사가 스크립트를 다시 배포할 필요가 없습니다.
- 호출: `POST`, `Content-Type: text/plain;charset=utf-8`, 본문 JSON, `redirect: follow` → 응답 JSON. 사전 요청(preflight)이 없는 단순 요청입니다.
- 교사 동작은 **관리 열쇠**(설치 때 만들어 Script Properties에 저장, 교사 PC의 앱에만 보관)로, 학생 동작은 지금 서버와 같은 **반·번호(+학년) + 6자리 개인 코드**(첫 접속 때 새 코드로 변경, 틀리면 학생 단위 잠금)로 확인합니다.
- 동시 실행을 짧게 하려고:
  - 제출은 규칙을 캐시에서 읽어 검사한 뒤 **기록 시트에 한 줄 덧붙이기(`appendRow`) 한 번** — 스크립트 잠금도, 시트 읽기도 없습니다(테스트로 확인).
  - 신청 설정·학생 한 줄·학생별 마지막 제출은 CacheService에 6시간까지 둡니다. 캐시가 비면 시트를 한 번 읽어 다시 채웁니다.
  - 스크립트 잠금(LockService)은 드문 동작에만: 신청 만들기, 마감/다시 열기, 코드 변경, 틀린 코드 실패 수 올리기. 8초 안에 못 잡으면 `{ error, retry: true }`.
  - 클라이언트(`apps-script/client.js`의 `appsScriptCall`)는 잠금 실패·JSON이 아닌 답(구글의 한도·오류 화면)·429·5xx·연결 실패 때 지연을 0.5초부터 두 배씩(최대 8초) 늘려 자동으로 다시 시도합니다. 규칙 위반 같은 정상 답은 다시 시도하지 않습니다.

## 2. 지금 서버(Supabase RPC)와의 대응표

| `get_course_login_form` | `loginForm` | 있음 | 같음(학교·학년도·차수·학년 목록, 학생 정보 없음) |

| `change_course_code` | `changeCode` | 있음 | 같음(6자리, 받은 코드와 달라야, 쉬운 번호 거절) |

| 행 보안(교사 계정별 분리) | 스프레드시트 자체가 교사 것 | **달라짐** | 분리 단위가 '교사의 스프레드시트'. 웹 앱 주소를 아는 사람은 누구나 요청할 수 있으므로 교사 동작은 관리 열쇠가 유일한 문 |
| Realtime(다른 창의 변경 알림) | 없음 | **빠짐** | 교사 화면은 '새로고침'으로 `results`를 다시 읽어야 함 |
| 학년도 종료 뒤 접근 차단(`course_school_year_active`) | 같은 날짜 계산 | 있음 | 다음 해 3월 1일 0시(한국 시각)부터 학생 접속·신청 만들기 거절. 자료 삭제는 교사가 스프레드시트에서 |
| 코드 해시(학생 id + 서버 후추) | SHA-256(소금 + 신청 id + 학년-반-번호 + 코드) | 있음 | 소금은 Script Properties. 시트에는 코드 원문이 없음. 스프레드시트를 보는 사람(교사 본인)은 6자리 코드를 대입으로 알아낼 수 있음(지금 서버의 운영자와 같은 위치) |

테스트봇(`test-bot-core.js`)·자동 테스트는 이 저장소에 연결하지 않았습니다(본 구현 범위).

## 3. 설치 순서(교사가 하는 일)

화면 문구는 구글이 바꿀 수 있습니다. 아래 ③~⑤의 경고 화면 문구와 유무는 **확인 못 함**(일반적으로 알려진 흐름을 적었습니다).

1. **스프레드시트 만들기** — 구글 드라이브에서 새 스프레드시트를 만듭니다(이름 예: `수강신청 저장소`). 본 구현 때는 운영자가 만든 원본의 '사본 만들기' 링크를 주는 방식이 더 쉽습니다(스크립트가 함께 복사됨 — 사본에 스크립트가 따라오는지는 일반적으로 그렇다고 알려져 있으나 **확인 못 함**).
2. **스크립트 붙이기** — 메뉴 `확장 프로그램 → Apps Script`. 처음 보이는 `Code.gs` 내용을 모두 지우고 `apps-script/Code.gs` 내용을 붙여 넣은 뒤 저장(💾).
3. **관리 열쇠 만들기** — 스프레드시트 화면으로 돌아가 새로고침하면 메뉴에 `수강신청`이 생깁니다. `수강신청 → 관리 열쇠 만들기`를 누릅니다. 처음에는 구글이 '승인 필요' 창을 띄웁니다 → 계정 선택 → **'Google에서 확인하지 않은 앱'** 화면이 나오면 `고급` → `(프로젝트 이름)(으)로 이동(안전하지 않음)` → `허용`. 이 경고는 '본인이 만든 스크립트를 본인 계정에서 실행'할 때 나오는 것으로, 승인하는 권한은 '이 스프레드시트 보기·수정'입니다. 승인 뒤 다시 `관리 열쇠 만들기`를 누르면 열쇠가 창에 나옵니다. 복사해 둡니다(나중에 `관리 열쇠 보기`로 다시 볼 수 있음).
4. **웹 앱으로 배포** — Apps Script 화면 오른쪽 위 `배포 → 새 배포` → 유형 선택(톱니) `웹 앱` → 설명 아무 글자, **다음 사용자 인증 정보로 실행: 나**, **액세스 권한이 있는 사용자: 모든 사용자** → `배포`. 나오는 **웹 앱 URL**(`https://script.google.com/macros/s/…/exec`)을 복사합니다.
5. **확인** — 그 주소를 브라우저 주소창에 넣어 열면 `{"ok":true,…"수강신청 저장소가 켜져 있습니다…"}`가 보여야 합니다. 로그인 화면이나 오류가 나오면 4번의 '모든 사용자' 설정을 확인합니다.
6. **앱에 넣기** — (본 구현 뒤) 2단계 웹 수강신청 설정에 웹 앱 주소와 관리 열쇠를 넣습니다. 시제품 단계에서는 `apps-script/load-test.html`을 브라우저로 열어 같은 두 값을 넣고 부하를 잽니다.
7. **스크립트를 고쳤을 때** — Code.gs를 바꾼 뒤에는 `배포 → 배포 관리 → 연필(수정) → 버전: 새 버전 → 배포`를 해야 같은 주소로 새 코드가 돕니다(`새 배포`를 누르면 주소가 바뀝니다).

## 4. 부하 측정(`apps-script/load-test.html`)

- 브라우저로 파일을 열어 웹 앱 주소·관리 열쇠·반 수·반별 인원을 넣고 `측정 시작`. **가상 학생만** 만들며(`가상학생1-1` …) 실제 학생 자료를 넣는 칸은 없습니다.
- 순서: 연결 확인 → 가상 신청 만들기 → (준비) 첫 접속·코드 변경을 10명씩 → (측정) 모든 학생이 한꺼번에 신청 화면 열기 → 한꺼번에 제출 → 결과 읽기로 저장된 수 대조 → 마감.
- 표: 단계별 요청 수·성공·성공률·다시 시도한 요청·다시 시도 횟수·응답 시간 중앙값/95%/최대·실패 종류(quota/busy/network/rule).
- 권하는 측정: 120명(4반 × 30)과 300명 안팎을 '제출 동시 수 0(한꺼번에)'으로, 그리고 30·60으로 나눠서. 볼 것은 ① 다시 시도까지 포함한 최종 성공률이 100%인지 ② 95% 응답 시간 ③ quota 실패가 몇 번째 시도에서 풀리는지.
- 끝나면 스프레드시트에서 `명렬_…`·`기록_…` 시트 두 장을 지웁니다.

## 5. 알려진 한계·위험

| 항목 | 내용 | 확인 |
|---|---|---|
| 동시 실행 한도 | 구글 문서의 할당량 표에 '동시 실행 30(사용자당)'이 있음. 웹 앱을 '나'로 실행하면 모든 학생 요청이 교사 한 계정의 실행으로 셈. 한 반이 동시에 누르면(30명) 한도에 닿음 → 자동 재시도로 넘기는 설계. 한도를 넘었을 때 구글이 무엇을 돌려주는지(HTML 오류 화면? HTTP 상태?)는 | **확인 못 함** — 측정 도구는 JSON이 아닌 답을 모두 quota로 세고 다시 시도 |
| 응답 시간 | 웹 앱 호출은 보통 1~3초로 알려짐(지금 서버는 0.1~0.3초). 학생 화면에 '저장 중…' 표시와 중복 누름 방지가 필요 | **확인 못 함**(측정 필요) |
| 하루 사용량 | 개인 계정의 하루 실행 시간·속성 읽기/쓰기 횟수 할당량이 있음. 학생 300명 × 요청 4~6번 × 1~3초는 통상 범위 안으로 보이나 수치는 | **확인 못 함** |
| 다른 출처에서의 fetch(CORS) | text/plain 단순 POST + redirect follow가 다른 출처(우리 홈페이지)에서 되는지, 모바일 브라우저(사파리·삼성 인터넷)·학교 와이파이에서도 되는지 | **확인 못 함** — ping 단계에서 network 실패로 드러남 |
| 경고 화면 | 설치 때 'Google에서 확인하지 않은 앱' 화면. 학생에게는 나오지 않아야 함(실행: 나) | 학생 쪽 무경고 여부 **확인 못 함** |
| 스크립트 갱신 | Code.gs가 바뀌면 교사마다 새 버전 배포를 해야 함. 그래서 규칙은 스크립트가 아니라 `setup`으로 보내는 자료에 두고, 응답의 `protocol` 번호로 앱이 '스크립트가 오래됨'을 알릴 수 있게 함 | — |
| 캐시 | 교사가 시트를 손으로 고치면 최대 6시간(학생 한 줄)·10분(없는 학생 판정) 늦게 반영될 수 있음. 캐시는 구글이 먼저 비울 수 있으나 그때는 시트를 다시 읽음(테스트로 확인) | — |
| 제출 순서 | 같은 학생이 거의 동시에 두 번 내면 시트에 늦게 붙은 줄이 유효. 재선택 대상이 아닌 학생 검사는 '지금 유효한 선택과 같아야 함'으로 판정 | — |

## 6. 본 구현 때 갈아 끼우는 방법과 예상 작업량

`supabase-client.js`(약 2,100줄)는 서버 호출을 `rpc(name, args, authenticated)` 한 함수로 합니다(218행 근처). 갈아 끼우는 지점은 세 곳입니다.

1. **저장소 종류 선택**: 설정값 `cloudStore = "supabase" | "apps-script"`(+ 웹 앱 주소, 관리 열쇠 — 이 PC의 작업 자료에만 저장, 백업 파일에 넣을지는 결정 필요). 학생 링크는 `#event=<id>&s=<웹 앱 배포 id>`처럼 저장소 주소를 함께 실어야 학생 화면이 어느 스크립트로 보낼지 압니다.
2. **호출 계층**: `rpc()`를 `store.call(name, args)`로 감싸고, Apps Script일 때는 RPC 이름 → 동작(`get_student_course_application` → `open` 등, 2절 표)으로 바꿔 `appsScriptCall`을 부릅니다. 오류는 지금 `{ error }` 처리와 같은 모양입니다.
3. **로그인·실시간**: 교사 구글 로그인(Supabase Auth)·세션·5분 자동 로그아웃·Realtime을 Apps Script 방식에서는 쓰지 않도록 분기(관리 열쇠 입력으로 대체, 결과는 새로고침).

| 작업 | 크기 |
|---|---|
| 저장소 선택 설정·학생 링크에 저장소 주소 싣기 | 작음 |
| 호출 계층(rpc 이름 ↔ 동작), 재시도·'저장 중' 표시 | 중간 |
| 빠진 동작 추가: 코드 재발급·잠금 해제·교사 대리 수정·삭제·다음 차수 계산(앱에서) | 중간~큼 |
| 로그인·Realtime 분기, 교사 화면 문구 | 중간 |
| 테스트봇·전과정 하네스에 Apps Script 흉내 서버 연결 | 중간 |
| 설치 안내 화면(사본 링크·주소/열쇠 입력·ping 확인) | 작음~중간 |
| 합계 | 지금 서버 방식을 유지한 채 둘째 저장소를 더하는 일 — 부하 측정이 통과한 뒤 시작 권장 |

## 7. 사용자 제안에서 찾은 오류 가능성(구현 전에 볼 것)

- **"로그인한 교사의 계정에 저장"**: 이 구조에서 교사는 앱에 구글 로그인을 하지 않습니다. '교사가 자기 계정에 배포한 스크립트'가 저장하는 것이고, 앱은 주소와 관리 열쇠만 압니다. 로그인 한 번으로 끝나지 않고 3절의 설치(스크립트 붙이기·경고 화면·배포)를 교사가 해야 합니다 — 다른 학교 교사에게는 이것이 가장 큰 문턱입니다.
- **동시 30**: 수강신청을 수업 시간에 한 반씩 하면 견딜 가능성이 있지만, 학년 전체가 같은 시각에 열면 재시도에 기대게 됩니다. 측정 없이 본 구현을 시작하면 안 됩니다.
- **개인 Gmail**: 5절 '개인 계정에 학생 자료' 참고.
- **대안과의 비교**: 구글 폼 방식은 설치가 없고 동시 한도 걱정이 적지만 개인 코드·택n 강제·재신청 잠금이 약합니다. 이 방식은 규칙은 지금과 같지만 설치·한도 부담이 있습니다.
