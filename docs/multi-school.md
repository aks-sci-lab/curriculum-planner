# 다른 학교에서도 쓰기 — 계획과 정한 것

점검 보고서는 `docs/multi-school-audit.md`. 이 문서는 **무엇을 어떤 순서로 하는지, 정한 기본값, 운영자·사용자가 직접 해야 하는 일**만 적습니다.

## 범위(사용자 결정 2026-11-13)

- 대상은 **울산 지역 일반고**. 다른 시도는 대상이 아님 → 울산 편제 점검 프로그램·교육청 양식 기능은 그대로 두고 문구만 '울산 편제 점검 프로그램용'으로.
- 웹 수강신청은 지금 구조 그대로(공용 Supabase + 교사 본인 구글 로그인, 교사 계정별 행 보안 분리).
- 배포: 한 홈페이지 주소를 모든 학교가 함께 씀(자료는 각 PC). 학교마다 다른 것은 '학교 설정'으로 두고 파일로 내보내기/가져오기.

## 1차 순서

| 걸음 | 내용 | 상태 |
|---|---|---|
| 1 | 편제표가 안 읽힐 때 이유·해결 방법 보여 주기(`layout.planDataError`) | 완료 |
| 2 | 편제표 넣는 길 안내: ① 울산 편제 점검 프로그램 파일 그대로 ② 학교 양식(예시·빈 양식 내려받기) | 완료 |
| 3 | 첫 실행 안내, 학년도 기본값 = 오늘 날짜 기준 | 완료 |
| 4 | '울산 편제 점검 프로그램' 문구 정리 | 완료 |
| 5 | 웹 수강신청 안전장치(안내·확인, 교사 삭제, 서버 SQL 초안, 운영자 할 일) | 완료(SQL은 초안 파일만 · 서버 미적용) |
| 6 | 학교 설정 한곳 + 내보내기/가져오기, 새 학교 기본값은 중립값 | 완료 |

## 정한 것(질문 없이 정한 기본값 — 한 줄씩)

- 새 코드는 `school-guide.js`(편제표 안내·예시 양식·첫 실행)와 `school-settings.js`(학교 설정)에 두고 `app.js`는 `typeof` 가드로 부르는 몇 줄만 고친다.
- 데이터 변환에 실패한 편제표는 지금처럼 표로는 불러오되(자료를 잃지 않게) **빨간 상태 문구 + 카드 단추 '읽지 못함 · 이유 보기' + 이유·해결 창**을 낸다. 조용히 넘어가지 않는다.
- 예시·빈 양식은 앱이 그 자리에서 만든다(가상 과목, 저장소에 파일을 두지 않음). 앱의 변환기로 다시 읽히는지 테스트로 보장한다.

- 시트가 여럿인 파일은 과목 데이터로 읽힌 시트 → 학기 열이 있는 표 → 과목 행만 있는 표 순으로 고른다(안내문 시트가 편제표를 밀어내지 않게).
- 학년도 기본값: 3월부터 그 해, 1·2월은 전 해(학년도 = 지금 재학 중인 학년도, 수강신청을 받는 해). 저장된 학년도가 있으면 그대로.
- '처음 시작 안내'는 1단계 맨 위에 두고 학교 이름·편제표 3개(내년도·올해·전년도 입학생)·결과가 갖춰지거나 '안내 닫기'를 누르면 사라진다(닫음은 브라우저에 기억).
- '교육청 양식으로 내보내기' → '울산 편제 점검 양식으로 내보내기'(파일 이름도 `_울산편제점검양식.xlsx`). 교육청 선택 설정은 만들지 않음(범위가 울산뿐).
- 웹 수강신청 생성 전 확인 창은 같은 브라우저·같은 학년도에서 한 번만 묻고, 같은 글을 생성 단추 아래 접힌 안내로 늘 둔다. 2차 이후 생성(이미 서버에 있는 명렬을 씀)에는 다시 묻지 않는다.
- 학교 이름이 2자 미만이면 웹 수강신청을 만들지 않는다(서버 초안도 2~60자).
- 서버 초안 한도: 계정당 수강신청 30개, 계정당 학생 합계 20,000명(운영자가 `course_limits`에서 바꿈). 근거: 한 학교 1년 = 차수 3~4개 × 학년 묶음 + 자동 테스트 몇 개.
- 자동 삭제는 기존 초안 `03-retention-purge.sql`(학년도 종료 +180일)을 그대로 쓰고 새로 만들지 않았다.
- 테스트봇(수강신청 자동 테스트)은 그대로 둔다: 가상 학생만 쓰고 끝나면 지우며, 04를 적용하면 계정 한도 안에서만 만들어진다. 다른 학교 사용자에게는 '[테스트] 학교이름' 신청이 자기 목록에만 보인다.

- 학교 설정(`자료 관리 → 학교 설정 (기준값)`)은 값을 따로 저장하지 않고 **원래 저장 위치를 읽고 쓴다**: 4단계 집계 기준 칸, `state.hoursStats[내년도]`(증원 19·순회 13·창체), `state.timetable.settings`(점심·참고 상한 22·진로 10·창체 5교시부터). 그래서 각 단계 화면과 항상 같은 값이다.
- 학교 설정 파일(`type: "curriculum-school-settings"`, version 1, `.json`)에는 위 숫자 13개 + 편제 점검 기준값(`curriculumCompliance.settings`) + 시간표 조건 일부(요일별 교시·창체·장소·규칙·다른 교과 교사 허용 교과·2시간 연속 과목)만 싣는다. **학생·교사 이름, 명렬, 결과, 학급 수·교사 수, 칸/교사 고정, 담임, 반 배정은 싣지 않는다.** 학교 이름은 파일 이름·확인 창 표시용으로만 싣고 가져올 때 덮어쓰지 않는다.
- **새 학교 중립 기본값은 점심 하나만 다르다**(모든 학년 4교시 뒤; 예전 기본값은 3학년만 3교시 뒤). 90/110/34, 19/13, 22, 진로 10, 창체 2(자율 1 + 진로 1)는 일반적인 값이라 그대로 두고 학교 설정 화면에서 '처음 값 그대로'로 표시한다.
- 하위 호환 방법: 코드 기본값(`TIMETABLE_DEFAULT_LUNCH`)은 그대로 두고, **저장된 자료가 없는 브라우저로 처음 열 때(전체 초기화 직후 포함)** 에만 `state.timetable.settings.lunchAfter = {1:4, 2:4, 3:4}`를 넣는다(`schoolSettingsFreshWorkspace`). 저장 자료가 있는 기존 사용자·예전 백업 복원은 예전 기본값(3학년 3교시 뒤) 그대로. → 기존 학교도 '전체 초기화'를 하면 중립값으로 시작하므로 3학년 점심을 다시 넣거나 학교 설정 파일을 가져와야 한다.
- 학교 설정 진입점은 맨 위 '자료 관리' 메뉴에 두었다(백업·초기화와 같은 성격). 확정된 차수에서는 4단계 집계 기준 세 칸을 잠근다(4단계와 같은 규칙).

## 사용자·운영자가 직접 해야 하는 일

### 운영자(이 앱을 운영하는 학교의 담당 교사)

1. **구글 로그인 동의 화면 게시 상태 확인** — Google Cloud Console → API 및 서비스 → OAuth 동의 화면. '테스트' 상태면 Test users에 등록한 계정만 로그인됩니다 → 다른 학교 교사가 쓰려면 **'프로덕션으로 게시'**(요청 범위가 이메일·프로필뿐이면 구글 심사 없이 게시됨) 또는 교사 계정을 한 명씩 Test users에 등록(100명 한도). 지금 상태는 이 세션에서 확인하지 못했습니다.
2. **서버 SQL 적용 상태 확인과 순서** — Supabase 대시보드 → SQL Editor. `supabase/upgrade-*.sql` 전체 → `proposed/01-code-hardening.sql`(앱이 이미 새 입구를 부르므로 적용돼 있어야 학생 접속이 됨 — 적용 여부 확인) → `02` → `03-retention-purge.sql`(+ pg_cron 예약) → **`04-multi-school-limits.sql`**. 모두 신청을 받고 있지 않은 시간에. 04는 01·03 없이도 실행됩니다.
3. **04 적용 뒤 앱 연결(다음 걸음)** — 학년도가 끝난 신청을 교사가 직접 지우는 화면(`list_own_course_events`·`delete_own_course_event`·`delete_all_own_course_events`)은 SQL이 적용된 뒤에 붙입니다. 적용 전에 붙이면 '서버 설정 필요' 오류만 납니다.
4. **Supabase 한도 확인** — 요금제(무료: DB 500MB, 일시 중지 정책, 동시 접속·Realtime 한도), 백업 여부. 학생 1명 ≈ 1~2KB(이력 포함)로 보면 1만 명 ≈ 10~20MB. 수강신청 기간에 여러 학교가 겹치면 동시 접속이 먼저 찹니다.
5. **개인정보 처리** — 다른 학교 학생의 성명·학년·반·번호·선택이 운영자 프로젝트에 저장되므로 운영자는 사실상 수탁자 위치가 됩니다. 운영 학교 차원의 결정(안내문·위탁 관계 문서화·대시보드 접근 계정 관리)이 필요합니다. 코드로는 해결되지 않습니다.
6. **홈페이지 주소를 바꾸지 않기** — 자료가 주소(origin)별 브라우저 저장소에 있어, 주소가 바뀌면 모든 학교가 백업 → 복원해야 합니다. 구글 로그인 되돌아오기 주소(Supabase Redirect URLs)도 지금 주소 하나만 등록돼 있으면 됩니다.

### 다른 학교 사용자(교육과정 담당 교사)

1. 맨 위 '학교·학년도 설정'에서 학교 이름·학년도를 넣는다.
2. 입학생 카드마다 편제표를 올린다 — 울산 편제 점검 프로그램 파일을 그대로, 또는 학교 양식(.xlsx, '편제표 넣는 방법'의 예시 참고).
3. 웹 수강신청을 쓰려면 본인 구글 계정으로 로그인하고, 생성 전 안내(학생 정보가 공용 서버에 저장됨)를 읽고 학교의 개인정보 처리 절차를 확인한다. 신청이 끝나 결과를 PC로 가져오면 '명렬·결과 영구 삭제'로 서버 자료를 지운다(다음 해 3월 1일 전에).
4. 담당자가 바뀌면 자료 관리 메뉴의 백업 파일을 넘긴다(서버의 신청은 만든 구글 계정에만 보이므로 진행 중인 신청은 그 계정으로 마무리).



## 사용자 결정에서 찾은 허점

- **"본인 구글 계정으로 로그인"만으로는 학교 소속이 확인되지 않는다.** 구글 계정이 있으면 누구나 신청을 만들 수 있다(학생·외부인 포함). 행 보안으로 남의 자료는 못 보지만 서버 용량은 쓸 수 있다 → 04 초안의 계정당 한도로 피해 크기만 줄였다. 더 막으려면 허용 계정 목록(운영자가 등록) 또는 교육청 도메인 제한이 필요 — 결정 필요.
- **"교사 계정별 분리"는 학교 단위 공유가 아니다.** 같은 학교의 다른 교사는 그 신청을 볼 수 없고, 담당자가 바뀌면 계정을 넘겨받거나 새로 만들어야 한다. 1차에서는 안내만 했다.
- **학년도가 끝나면 교사가 자기 자료를 지울 수 없다**(지금 서버: 다음 해 3월 1일부터 목록·삭제 모두 막힘, 자동 삭제 03은 적용 여부 미확인). 즉 지금 상태로 다른 학교에 열면 지우지 않은 학생 자료가 운영자 서버에 계속 남는다 → 화면 안내(그 전에 지우기) + 04 초안(끝난 신청도 지우는 입구) + 03 적용 권고.
- **운영자가 다른 학교 학생 자료에 접근할 수 있다**(대시보드). 안내문에 그대로 적었다. 이것을 원하지 않는 학교는 웹 수강신청을 쓰지 않고 결과 엑셀을 올리는 길을 쓴다.
- **"한 주소를 함께 씀"**: main에 합치면 모든 학교가 동시에 새 버전을 받는다 → 수강신청 기간에는 배포를 피하고, 편제표 변환기 버전을 올리면 모든 학교 자료가 열 때 재변환된다(다른 양식에서의 안전성은 예시 양식·울산 파일 경로로만 확인).
- **울산 편제 점검 프로그램 파일이 '모든 학교에 있다'는 전제**: 파일은 있어도 「N학년_편성과목」에 과목을 입력·저장하지 않은 상태면 읽을 과목이 없다(그때는 안내 문구가 나옴). 실제 다른 학교 파일로는 시험하지 못했다(이 세션에 실제 자료 없음).
